# 프론트엔드 구독 플랜 제한·폴더 잠금 적용 가이드

기준: 2026-09-08, `dev`의 PR #151~#155 반영 상태(커밋 `9a1bd18`). 웹·앱 프론트엔드가 구현할 화면 동작과 실제 HTTP 계약을 정리한다. **현재 구현된 정책**과 **프론트엔드 적용 권장 사항**을 구분하며, 이전 검수 문서의 미채택 대안을 제품 정책으로 적용하지 않는다. 이름(`title`) 단독 수정은 #156에서 추가했으며, 서비스에 해당 수정이 배포되었는지 확인해야 한다.

## 1. 적용할 정책

| 기능                         | 유효 Free                                                    | 유효 Pro                      |
| ---------------------------- | ------------------------------------------------------------ | ----------------------------- |
| 폴더 콘텐츠 열람·편집        | 서버가 선정한 1개만 가능                                     | 모든 활성 폴더 가능           |
| 다른 기존 폴더               | 데이터 보존, 콘텐츠 접근 차단                                | 접근 가능                     |
| 폴더 목록                    | 잠긴 폴더의 이름·ID 등 관리 정보와 `isLocked` 표시           | 전체 표시                     |
| 새 폴더                      | 활성 폴더가 없어야 함; 선택 폴더가 휴지통에 있으면 복구 필요 | 현재 플랜별 폴더 수 상한 없음 |
| 폴더 재정렬                  | 차단                                                         | 허용                          |
| 클립 추가 저장               | 폴더당 활성 클립 50개까지                                    | 폴더당 활성 클립 300개까지    |
| 이미 한도를 초과한 클립      | 보존; 접근 폴더에서는 수정·삭제 가능                         | 보존; 수정·삭제 가능          |
| 태그 조회·편집·검색          | 접근 폴더에서 기존 기능 유지                                 | 기존 기능 유지                |
| 잠긴 폴더 자체 삭제          | 관리 작업으로 허용                                           | 허용                          |
| 휴지통 영구 삭제·전체 비우기 | 소유 데이터 정리 허용, 숨겨진 항목도 전체 비우기에 포함      | 동일                          |

50/300은 사용자 전체 합계나 절대 보관량이 아닌 **폴더별 추가 저장 한도**다. Free로 내려간 200개 폴더를 50개로 잘라 표시하거나 초과분을 삭제하지 않는다. 접근 가능한 폴더라면 200개 모두 페이지를 넘겨 열람할 수 있다. 단, 새 클립을 추가하려면 49개 이하로 줄이거나 유효 Pro가 되어야 한다. Pro도 300개를 넘는 추가 저장은 불가능하다.

**적용하지 않는 정책:** 모든 폴더 읽기 허용, 사용자 임의 접근 폴더 전환, 삭제 후 다음 폴더 자동 개방, 클립 이동, Free 전체 태그 차단, Free 응답의 일괄 `tags: []` 변환.

## 2. 유효 플랜과 구독 화면

### 공개 API

경로는 서버 기준 상대 경로이며 코드에는 `/api` 전역 접두사가 없다. 실제 서비스의 게이트웨이 base URL을 사용한다. 아래 API는 모두 `Authorization: Bearer <accessToken>` 인증이 필요하다.

| API                                           | 요청                                               | 성공 응답                                                          |
| --------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------ |
| `GET /subscriptions/me`                       | 없음                                               | 200, `Subscription`                                                |
| `PATCH /subscriptions/me`                     | `{ "type": "CANCEL" }` 또는 `{ "type": "RESUME" }` | 200, `Subscription`; CANCEL에는 `cancellation` 추가                |
| `POST /subscriptions/me/billing-auth/request` | 없음                                               | 201, `clientKey`, `customerKey`, `method`, `successUrl`, `failUrl` |
| `POST /subscriptions/me/billing-auth/confirm` | `{ "authKey": "...", "customerKey": "..." }`       | 201, `Subscription`                                                |

```ts
type Subscription = {
  plan: 'FREE' | 'PRO';
  status: 'ACTIVE' | 'CANCELED' | 'EXPIRED';
  autoRenew: boolean;
  currentPeriodEnd: string | null;
  nextBillingAt: string | null;
  provider: 'TOSS_PAYMENTS' | null;
};
type CancelResponse = Subscription & {
  cancellation: { pendingRenewalPayment: boolean; message: string };
};
```

JSON 날짜는 ISO 문자열이다. 화면의 요금제 예상 권한은 아래처럼 계산할 수 있으나 **서버의 폴더 잠금 응답과 쓰기 결과가 최종 기준**이다. 클라이언트 시계나 오래된 구독 캐시만으로 잠금을 해제하지 않는다.

```ts
function hasEstimatedProAccess(s: Subscription, now = Date.now()): boolean {
  const end = s.currentPeriodEnd ? Date.parse(s.currentPeriodEnd) : NaN;
  return (
    s.plan === 'PRO' &&
    (s.status === 'ACTIVE' || s.status === 'CANCELED') &&
    Number.isFinite(end) &&
    end > now
  );
}
```

- `CANCELED`여도 결제한 기간이 남아 있으면 Pro다. 해지 버튼을 눌렀다고 바로 Free UI로 바꾸지 않는다.
- `PRO/ACTIVE/autoRenew=true`여도 종료 시각이 지났으면 리소스 API는 Free로 제한한다. 구독 GET은 이 조합을 즉시 `FREE`로 정규화하지 않을 수 있다.
- 종료 시각이 없거나 종료 시각과 현재 시각이 같으면 Pro로 계산하지 않는다. 서버와 시계 차이가 있으면 재조회 결과를 우선한다.
- `autoRenew`는 다음 자동결제 의사이고 현재 사용 권한이 아니다. `nextBillingAt=null`도 곧바로 Free를 뜻하지 않는다.

### 해지·재개·결제 인증

CANCEL은 다음 자동결제를 중단하며 이미 결제한 기간을 줄이지 않는다. 응답의 `cancellation.message`를 표시한다. `pendingRenewalPayment=true`면 이미 시작한 이번 청구가 완료되고 이용 기간이 연장될 수 있음을 안내한다. `false`도 과금 없음이나 환불 완료를 보장하지 않는다. 이 값은 해지 응답 시점의 정보이며 일반 GET에는 없다.

RESUME은 잔여 Pro 기간과 저장된 결제수단이 있는 해지 구독에서만 가능하다. 성공하면 즉시 과금 없이 자동갱신이 다시 켜지며, 불가능한 상태는 409다. 서버가 결제수단 키를 공개하지 않으므로 상태만 보고 성공을 단정하지 않는다.

결제수단 인증은 request 응답 → Toss 인증 → 성공 리다이렉트의 `authKey/customerKey`를 confirm으로 전달하는 순서다. 리다이렉트 도착만으로 Pro를 표시하지 말고 confirm 성공 후 구독과 폴더를 다시 읽는다. confirm도 재개 조건이면 즉시 결제 없이 재개할 수 있다.

**중복 청구 예방:** confirm의 네트워크 타임아웃·응답 유실에 자동 재전송을 붙이지 않는다. 현재 최초 결제 confirm에는 클라이언트 멱등키 계약이 없다. 이전 자동결제 결과 확인 중인 경우와 신규 결제 실패 모두 409가 가능하며 전용 `code`도 없다. 서버 메시지를 표시하고 구독 상태를 확인한다. 화면에 무조건 새 결제를 권하지 않는다. 자동갱신 결과 대사는 백엔드가 수행하며 운영용 `/subscriptions/auto-renewals/due`를 프론트에서 호출하지 않는다.

## 3. 폴더 목록·잠금 화면

`GET /folders`는 배열을 반환한다. 아래는 화면에서 사용할 주요 필드만 발췌한 예시다.

```json
[
  { "id": "folder-a", "name": "업무", "order": 0, "isLocked": false },
  { "id": "folder-b", "name": "개인", "order": 1, "isLocked": true }
]
```

전체 폴더 객체에는 `workspaceId`, `createdAt`, `updatedAt`, `deletedAt`도 있다. 목록의 `isLocked`로 잠금 배지를 표시한다. 다른 폴더 변경 응답에는 이 필드가 없을 수 있으므로 부분 응답으로 기존 잠금 정보를 덮어쓰지 않는다. 예상한 목록 필드가 없으면 잠금을 모두 해제하는 대신 로딩/호환성 상태로 처리하고 최신 API 응답을 확인한다.

| 화면/작업               | 적용 방법                                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 잠긴 폴더 클릭·딥링크   | 콘텐츠 대신 잠금 안내와 Pro 이용 안내 표시                                                                                               |
| 미리보기·복사·검색 결과 | 캐시에 남은 잠긴 클립의 제목·본문·색상·이미지도 렌더링하지 않음                                                                          |
| 폴더 목록 관리          | 이름·잠금 표시와 폴더 자체 삭제 유지; 잠긴 폴더 이름 변경은 차단                                                                         |
| 폴더 재정렬             | Free에서 드래그/재정렬 메뉴 비활성화                                                                                                     |
| 접근 폴더 없음          | 목록이 비어 있으면 새 폴더 생성도 제공; 선택 폴더 복구 필요 오류이면 휴지통 안내. 기존 폴더가 모두 잠겼다면 임의 개방 없이 복구·Pro 안내 |
| 태그                    | 접근 폴더에서는 기존대로 사용; 잠긴 폴더 태그를 별도 패널에서 노출하지 않음                                                              |

### 선정·삭제·복구 규칙

서버는 첫 Free 접근에서 `order ASC, id ASC`로 활성 폴더 하나를 선정하고 같은 구독 기간에는 고정한다. 프론트에서 “마지막 방문 폴더”로 바꾸거나 “Free 사용 폴더 선택” 버튼을 만들지 않는다.

A가 접근 폴더이고 B가 잠긴 상태에서 A를 삭제하면, B는 계속 잠긴다. 목록의 모든 폴더가 잠긴 상태도 정상이다. A는 다른 잠긴 활성 폴더가 남아 있어도 복구 가능하다. B 등 다른 기존 폴더를 복구해 교대 접근할 수 없다.

선정 이력이 없고 활성 폴더도 없는 최초 상태에서는 한 폴더를 복구해 선택할 수 있다. 선정 폴더가 영구 삭제되고 활성 폴더도 없으면 새 빈 폴더를 만들 수 있지만 다른 기존 폴더가 열리지는 않는다. Pro 재구독 후에는 전체 접근이 열리며 다음 Free 기간에는 서버가 당시 순서로 다시 선정한다.

권장 삭제 문구: **“이 폴더를 삭제해도 다른 잠긴 폴더가 열리지 않습니다. 삭제한 폴더는 휴지통에서 복구할 수 있습니다.”** 휴지통 보존 기간은 서버 설정을 확인해 안내한다(백엔드 기본 30일, 배포 설정으로 변경 가능).

## 4. 목록·수정 API 연결 시 주의사항

| API                                                                               | 용도와 제약                                                                 |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `GET /folders/:id`                                                                | 잠긴 폴더 직접 조회는 403                                                   |
| `GET /clips?folderId=...&type=ALL`                                                | 해당 폴더 클립; `type` 필수                                                 |
| `GET /clips?favorite=true&type=ALL`                                               | 접근 가능한 즐겨찾기만 반환                                                 |
| `GET /clips?type=ALL` 또는 `recent=true&type=ALL`                                 | 기본 최근 목록; 전체 저장 클립 목록으로 간주하지 않음                       |
| `GET /clips/views/recent`                                                         | 최근 열람 최대 50개, `{ items }`; 페이지 커서 없음                          |
| `POST /clips`                                                                     | multipart `folderId` + `text` 또는 `file`; 최종 한도·잠금 검사              |
| `PATCH /clips/:id`                                                                | `title` 단독 또는 `text/file`과 함께 전달; `folderId/workspaceId` 전달 금지 |
| `PUT /clips/:clipId/tags`                                                         | 접근 클립의 태그 연결 변경                                                  |
| `POST /clips/:id/views`                                                           | 열람 기록, 성공 204; 응답 JSON 파싱하지 않음                                |
| `POST /clips/:id/likes`, `DELETE /clips/:id/likes`                                | 접근 클립 좋아요 변경                                                       |
| `DELETE /clips/:id`, `DELETE /clips`                                              | 단건·명시적 다중 삭제; 다중 body `{ "clipIds": ["..."] }`                   |
| `DELETE /clips/all/:folderId`                                                     | 접근 가능한 해당 폴더 내 전체 클립 삭제                                     |
| `POST /folders`, `PATCH /folders/:id`, `PATCH /folders/reorder`                   | 생성·이름 변경·재정렬에 서버 정책 적용                                      |
| `GET/POST /folders/:folderId/tags`, `PATCH/DELETE /folders/:folderId/tags/:tagId` | 해당 폴더 태그 접근도 잠금 검사                                             |
| `DELETE /folders/:id`                                                             | 폴더 자체를 휴지통으로 보냄; 잠긴 폴더도 관리 예외로 허용                   |

`folderId`와 `favorite/recent`를 함께 지정하거나 `favorite=true&recent=true`를 함께 보내면 400이다. `type`은 `TEXT/COLOR/IMAGE/ALL`, 검색어는 `q`를 사용한다. 제목에 일치하는 항목이 없으면 태그 검색으로 넘어가며 이 판정도 접근 가능한 데이터만 대상으로 한다. 클라이언트가 Pro 시절의 전체 캐시를 검색해 결과를 합치지 않는다.

클립 페이지 응답은 `{ items, hasMore, nextCursor }`다. 커서는 응답 값을 그대로 다음 요청에 사용하며 마지막 클립 ID로 다시 만들지 않는다. 특히 최근 목록 커서는 내부 열람 기록 ID일 수 있다. 조회 조건·계정·권한이 바뀌면 이전 커서를 폐기한다.

이름만 변경할 때는 `PATCH /clips/:id`에 `{ "title": "새 이름" }`을 전송한다. 기존 본문·이미지를 복사해서 함께 보내지 않는다. 이름은 공백이 아닌 문자열이어야 한다. 콘텐츠만 수정하면 이름이 본문·색상·파일명에서 다시 만들어지므로, 사용자 지정 이름을 유지하려면 콘텐츠 변경 시 `title`도 함께 보낸다.

수정 시 같은 폴더 ID라도 전송하면 400이며, 콘텐츠 없는 `{}` 수정도 400이다. 붙여넣기·열람 기록 갱신을 위해 빈 PATCH를 보내지 않는다. 열람은 views API를 사용한다. 클립 이동 UI는 제공하지 않는다.

## 5. 클립 한도와 오류 처리

페이지 `items.length`는 폴더 전체 개수가 아니다. 클립 페이지·폴더 응답에 `totalCount`, `remainingSlots`, `clipLimit`이 제공된다고 가정하지 않는다. 한도 차단과 정확한 현재 개수는 서버의 최종 결과를 기준으로 처리한다.

```json
{
  "statusCode": 409,
  "message": "폴더의 클립 추가 저장 한도(50개)를 초과합니다.",
  "error": "Conflict",
  "code": "CLIP_LIMIT_EXCEEDED",
  "details": {
    "resource": "clips",
    "folderId": "folder-a",
    "limit": 50,
    "currentCount": 50,
    "requestedIncrease": 1,
    "upgradeCanResolve": true
  }
}
```

| HTTP / `code`                 | 화면 처리                                                                                          |
| ----------------------------- | -------------------------------------------------------------------------------------------------- |
| 403 / `PROJECT_LOCKED`        | 콘텐츠 표시·편집 중단, 낙관적 변경 취소, 최신 폴더/구독 확인 후 잠금 안내                          |
| 409 / `CLIP_LIMIT_EXCEEDED`   | 개수와 한도 안내; `details.upgradeCanResolve === true`일 때만 이 한도의 해결책으로 업그레이드 표시 |
| 409 / `PLAN_LIMIT_EXCEEDED`   | 폴더 생성·복구 제한 안내; 선택 폴더가 휴지통에 있으면 복구 경로 안내                               |
| 403 / `FEATURE_NOT_AVAILABLE` | Free 재정렬 제한 안내; 다른 잠금 검사에서 먼저 `PROJECT_LOCKED`가 나올 수도 있음                   |
| 409 / `code` 없음             | 부모 폴더 복구 필요 등 일반 충돌 또는 구독 오류; 메시지 표시, 한도 오류로 단정하지 않음            |
| 404                           | 삭제·미소유·접근 범위 밖 커서 등 가능; 커서 요청이면 첫 페이지로 한 번 재시작                      |
| 400                           | 입력 계약 오류; 문구 또는 메시지 배열 표시, 동일 입력 자동 재시도 금지                             |
| 401                           | 기존 세션 갱신/로그인 흐름; 플랜 업그레이드 안내로 대체하지 않음                                   |

`code`와 `details`는 모든 오류의 필수 필드가 아니다. 일반 오류의 `message`는 문자열 또는 검증 메시지 배열일 수 있다. 알려진 `code`로 분기하되 알 수 없는 코드·누락 필드는 일반 오류 처리를 유지한다.

Free 50→51은 업그레이드로 해결 가능하지만 Free 300→301과 Pro 300→301은 불가능하다. 여러 폴더의 복구 중 하나라도 추가 후 300개를 넘으면 `upgradeCanResolve=false`다. 오류에는 실패한 대표 폴더 하나가 담길 수 있으므로 클라이언트가 그 한 건만 고친 뒤 나머지 요청의 성공을 보장하지 않는다. 이 값은 다른 접근·삭제 조건을 면제하지 않는다.

생성·수정·복구에서 403/409를 받으면 입력 중인 텍스트·파일을 유지하고 재시도 여부를 사용자가 결정하게 한다. 네트워크 오류는 커밋 성공 여부가 불명확할 수 있으므로 생성·복구 같은 변경 요청을 무조건 자동 재전송하지 않는다.

## 6. 휴지통 화면

| API                               | 계약                                                                                            |
| --------------------------------- | ----------------------------------------------------------------------------------------------- |
| `GET /trash?cursor=...&limit=...` | `{ items, nextCursor, hasNextPage }`; 클립 페이지의 `hasMore`와 구분                            |
| `PATCH /trash/restore`            | body `{ "items": [{ "itemType": "FOLDER", "id": "folder-a" }] }`; 성공 `{ "restoredCount": 1 }` |
| `DELETE /trash/items`             | 동일한 `items` 구조; 선택 영구 삭제                                                             |
| `DELETE /trash`                   | 전체 비우기; 본문 없음                                                                          |

영구 삭제 결과는 `{ clipsDeleted, foldersDeleted, totalDeleted }`다. `items`의 `itemType`은 `CLIP/FOLDER`이며 중복된 `itemType + id`는 HTTP 검증에서 400이다. 클라이언트 선택 목록을 중복 제거해 전송한다. 복구는 일괄 성공 또는 전체 실패이며, `restoredCount`는 요청 항목 수다. 폴더 안에서 다시 보이게 된 모든 클립의 수가 아니다.

삭제 폴더는 이름·ID·삭제 시각만 표시한다. 내부 클립을 미리보기로 읽지 않는다. 잠긴 활성 폴더의 삭제 클립은 휴지통 목록에 아예 나오지 않으며 마스킹 행을 생성하지 않는다. 반환된 클립 항목만 제목·유형을 표시한다.

- 선택된 Free 폴더에 기존 미삭제 클립이 200개 있어도 **폴더 자체 복구**는 허용된다. Pro 350개 폴더도 동일하다.
- 같은 요청에 별도로 삭제했던 클립 하나를 추가해 201/351개를 만드는 것은 한도 초과다. 폴더 복구 시 모든 자식을 `items`에 자동 추가하지 않는다.
- 삭제된 부모의 클립을 복구하려면 부모도 복구해야 한다. 부모만 복구하면 그 전에 개별 삭제했던 클립은 계속 휴지통에 남는다.
- 조회 결과에는 `canRestore`, `isLocked`, 과거 선택 폴더 ID가 없다. 삭제 폴더가 목록에 보인다고 복구 가능하다고 단정하지 않는다. 선택 ID를 모르면 복구 요청 결과로 안내한다.
- 휴지통 목록이 비어도 숨겨진 삭제 클립이 존재할 수 있다. “전체 비우기”를 표시된 항목만 삭제하는 기능으로 설명하거나 표시 개수를 전체 삭제 개수로 확정하지 않는다.
- 접근 범위에서 벗어난 휴지통 커서는 오류 대신 빈 페이지로 돌아올 수 있다. 권한 전환 후에는 반드시 커서를 초기화한다.

권장 전체 비우기 문구: **“현재 보이지 않는 잠긴 폴더의 삭제 항목도 영구 삭제됩니다. 영구 삭제한 자료는 복구할 수 없습니다.”**

## 7. 상태·캐시 갱신 권장 흐름

이 절은 프론트엔드 구현 권장 사항이며 특정 상태 관리 라이브러리를 요구하지 않는다.

1. 로그인/계정 변경 시 구독과 폴더 목록을 조회한다. 초기 잠금 상태 확인 전에는 이전 계정이나 이전 권한의 콘텐츠를 렌더링하지 않는다.
2. 최신 폴더 응답으로 라우트 접근을 판정한 뒤 콘텐츠를 요청한다. 잠금 화면에서도 폴더 관리 정보는 유지한다.
3. 해지·재개·결제 인증 완료, 예상 종료 시각 도달, 앱 복귀 시 구독과 폴더의 최신 상태를 확인한다. 앱이 잠들어 있으면 만료 타이머가 실행되지 않을 수 있으므로 복귀 시각도 확인한다.
4. 권한 범위가 달라지면 해당 계정의 폴더별/최근/즐겨찾기/검색/태그/휴지통 캐시와 커서·선택 상태를 무효화한다. 진행 중인 이전 요청은 취소하거나 요청 세대 값으로 응답을 버려 늦은 Pro 응답이 잠긴 화면을 다시 채우지 않게 한다.
5. 폴더 삭제·복구·생성 후에는 폴더 목록 및 관련 클립·휴지통을 갱신한다. 클립 생성·수정·삭제·복구는 영향을 받는 목록과 로컬 개수만 갱신한다. 한도 판단은 계속 서버에 맡긴다.
6. 좋아요 변경은 좋아요 관련 캐시, 열람 기록은 최근 열람 관련 상태를 갱신한다. **단순 조회나 views 기록 성공마다 구독·폴더·모든 클립을 재조회하지 않는다.** 권한 변화 감지와 실제 데이터 변경을 구분한다.

403/409 정책 오류에서 무한 재조회·자동 재전송 루프를 만들지 않는다. 권한 재확인은 묶어서 한 번 수행하고, 계속 실패하면 안내 상태로 유지한다. 데이터 보존 정책에 따라 사용자의 입력을 보존하되 잠긴 기존 콘텐츠를 미리보기·검색 인덱스에서 계속 노출하지 않는다.

## 8. 적용 순서와 완료 기준

백엔드에 `20260908080000_add_free_folder_access` 마이그레이션과 PR #155가 배포되어야 한다. 로컬에 코드가 병합되었다는 사실만으로 서비스 배포를 완료한 것으로 보지 않는다. 실제 배포 환경에서 오류 코드와 `GET /folders`의 `isLocked`를 확인한다. 새 환경변수는 없다.

| 확인 시나리오                             | 기대 결과                                                  |
| ----------------------------------------- | ---------------------------------------------------------- |
| 잔여 기간이 있는 CANCELED                 | Pro 콘텐츠 유지, 다음 자동결제 중단 표시                   |

| Free A 접근/B 잠금                        | B의 라우트·미리보기·검색·즐겨찾기·태그·최근 열람 노출 없음 |
| A 삭제 → 목록에 B만 남음                  | B 자동 개방 없음; A 휴지통 복구 가능                       |
| 재구독 완료                               | 폴더 재조회 후 잠금 해제, 이전 커서 재사용 안 함           |
| Free 49→50 / Pro 299→300                  | 생성 성공; 다음 생성 한도 오류                             |
| Free 200개 보유                           | 접근 폴더의 기존 200개 열람·수정·삭제 가능; 추가 저장 제한 |

| 폴더 자체 복구 / 추가 삭제 클립 동반 복구 | 보존 예외와 추가 증가 검사를 구분                          |
| 잠긴/허용 항목을 섞은 다중 변경           | 전체 실패; 낙관적 부분 성공 상태 남지 않음                 |
| 업로드 도중 만료·다른 탭 마지막 슬롯 사용 | 오류 후 입력 유지; 허용된 것으로 단정하지 않음             |
| 늦게 도착한 Pro 응답                      | 잠긴 화면·캐시에 다시 반영되지 않음                        |
| 오래된 목록/휴지통 커서                   | 첫 페이지로 재시작, 무한 재시도 없음                       |
| 휴지통 전체 비우기                        | 숨겨진 항목 포함 안내와 서버 결과 개수 사용                |
| 빈 PATCH·folderId 포함 PATCH              | 전송하지 않음; 클립 이동 UI 없음                           |
| 자동갱신 처리 중 해지·confirm 결과 불명확 | 이번 청구 가능성 안내; 중복 결제 자동 재시도 없음          |

이전 백엔드 검증은 단위 251개·통합 71개 통과 상태다. 이 가이드 작성으로 프론트엔드 구현이나 브라우저 QA가 수행된 것은 아니다.

## 9. 계약의 한계와 근거

현재 API에는 통합 `effectivePlan/entitlements`, `freeAccessibleFolderId`, 폴더별 전체 클립 개수·남은 슬롯, 휴지통 `canRestore`, 실시간 권한 변경 이벤트, 공개 결제 대사 상태 조회 API가 없다. 이 정보를 서버가 제공하는 것처럼 타입·화면을 구현하지 않는다. 정확한 기능이 필요하면 별도 API 확장으로 합의한다.

Swagger에서 POST 결제 인증 API가 200으로 설명되어 있어도 현재 런타임 성공은 201이다. 최근 열람 응답 DTO에 `viewId`가 설명되어 있지만 `/clips/views/recent` 실제 유스케이스는 클립 항목을 반환하므로 이를 필수 키로 사용하지 않는다. 클립 페이지의 `nextCursor`는 서버가 준 값을 그대로 사용한다.

공개 이미지 URL을 이미 확보한 경우 객체 자체의 접근은 이번 API 잠금으로 회수되지 않는다. 오프라인에 저장한 자료의 회수도 포함하지 않는다. “기존 데이터 완전 차단/삭제”로 안내하지 않는다.
