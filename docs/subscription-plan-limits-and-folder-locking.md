# 구독 플랜 제한 및 다운그레이드 폴더 잠금 정책

> 상태: **클립 한도·Free 단일 폴더 접근 구현 · 나머지 정책 검토 중** · 검토일: 2026-09-08\
> 저장소 코드와 기존 문서를 대조한 결과다. #150에서 Free 폴더당 50개·Pro 300개, 기존 초과 데이터 보존과 폴더 자체 복구 예외를 확정했다. 확정 정책과 나머지 검토안을 함께 기록하며, 이번 #150 작업에서는 클립 생성·개별 복구의 플랜별 한도를 구현했다. Free 단일 폴더 접근·생성·복구 제한도 구현했다. 별도 태그 유료화는 포함하지 않는다. 제품 결정이 필요한 변경은 마지막 결정 표에 별도로 표시한다.

프론트엔드 구현·배포 적용은 [프론트엔드 구독 플랜·폴더 잠금 가이드](frontend-subscription-plan-and-folder-locking-guide.md)를 따른다. 실제 API 계약, 화면 동작, 오류·캐시 처리와 QA 항목을 정리했다.

Free는 한 폴더만 열람·편집하며 같은 구독 기간에는 선택을 고정한다. 구현 계약과 삭제·복구 예외는 [폴더 접근 문서](free-folder-access.md)를 따른다. 결제 신뢰성 검증과 이미지 경쟁 해결은 잠금 강제 배포의 전제다.

## 목적과 범위

개인 워크스페이스의 Free/Pro 플랜별 폴더 접근, 클립 한도, 태그 기능을 일관되게 제어한다.

- 이 문서에서 요금표의 **프로젝트**는 현재 백엔드의 `Folder`를 뜻한다.
- `Workspace`는 개인 사용자당 하나이므로 프로젝트 수 제한 대상으로 사용하지 않는다.
- 클립의 소속 폴더와 워크스페이스는 생성 시 결정하며 이후 변경할 수 없다. Free/Pro 모두 동일하다. 수정 API는 `folderId`·`workspaceId`를 받지 않으며, 같은 ID를 재전송해도 허용되지 않은 필드로 거부한다.
- 기기 연동 및 AI 기능 정책은 이 문서의 범위에서 제외한다.

## 플랜 정책

| 항목                | Free                                   | Pro                      |
| ------------------- | -------------------------------------- | ------------------------ |
| 접근 가능한 폴더 수 | 최대 1개                               | 모든 활성 폴더           |
| 폴더 생성·복구      | 작업 후 활성 폴더가 최대 1개일 때 허용 | 플랜상 개수 제한 없음    |
| 활성 클립 추가 저장 한도 | 폴더당 50개 | 폴더당 300개 |
| 정리 방식           | 제목 검색                              | 제목 검색 + 태그         |
| 태그                | 사용할 수 없음                         | 생성·수정·삭제·연결 가능 |

클립 한도는 #150에서 확정한 플랜별 **추가 저장 한도**다. 사용자 전체 합계가 아닌 각 폴더의 활성 클립 수를 기준으로, Free는 50개·Pro는 300개에 도달하면 생성·개별 삭제 클립 복구를 제한한다. 다운그레이드나 기존 초과 데이터는 자동 삭제하지 않고, 초과 클립 중 일부만 선정해 잠그지도 않는다. 접근 권한이 있는 폴더에서는 기존 자료의 열람·수정·삭제를 허용한다.

이 정책은 항상 보관량을 50개 이하로 줄이는 정책이 아니다. 단기 Pro 사용 후 Free에서 초과 자료를 계속 보관하는 동작을 수용하며 요금제 안내에도 보존 예외를 명시한다. 이 결정이 모든 폴더 열람이나 자유로운 접근 폴더 교대를 허용한다는 뜻은 아니다. 표의 폴더 접근·생성·복구와 태그 정책은 별도 기준안으로 남는다.

### 활성 데이터와 접근 가능 데이터의 정의

- 활성 폴더: `Folder.deletedAt IS NULL`
- 활성 클립: `Clip.deletedAt IS NULL` 이고 소속 `Folder.deletedAt IS NULL`
- 접근 가능 폴더: 활성 폴더 중 유효 플랜이 Pro이거나 `freeAccessibleFolderId`와 ID가 같은 폴더
- 잠긴 폴더: Free에서 접근 폴더로 선정되지 않은 활성 폴더. 삭제 상태와는 다르다.

잠긴 폴더와 그 안의 미삭제 클립은 여전히 활성 데이터다. Free 전환으로 활성 폴더가 여러 개 남는 것은 기존 데이터 보존을 위한 예외이며, 추가 생성·복구의 빈 슬롯으로 계산하지 않는다.

삭제된 폴더 안의 클립은 활성 한도에서 제외한다. 폴더 복구 시 `Clip.deletedAt IS NULL`인 클립만 자동으로 활성화된다. 폴더 삭제 전에 개별 삭제한 클립은 별도로 복구하지 않는 한 삭제 상태를 유지한다.

## 구독 기간과 유효 플랜

자동갱신 해지(`CANCELED`)는 즉시 Free 전환이 아니다. 사용자는 이미 결제한 `currentPeriodEnd`까지 Pro 권한을 유지한다.

| 구독 상태                            | `currentPeriodEnd` | 유효 플랜                                                            |
| ------------------------------------ | ------------------ | -------------------------------------------------------------------- |
| `PRO / ACTIVE` 또는 `PRO / CANCELED` | 미래               | Pro                                                                  |
| `PRO / ACTIVE` 또는 `PRO / CANCELED` | 현재 시각 이하     | Free. 아래 유예 정책을 채택한다면 명시적인 유예 종료 시각까지 예외   |
| `PRO / ACTIVE` 또는 `PRO / CANCELED` | `null`             | Pro를 입증할 기간 정보가 없으므로 Free로 판정하고 데이터 이상을 기록 |
| `FREE` 또는 `EXPIRED`                | 무관               | Free                                                                 |
| 구독 행 없음                         | 해당 없음          | Free. 기존 데이터는 유지하고 구독 기본 행을 복구                     |

- 전환 경계는 서버의 현재 시각과 `currentPeriodEnd`를 비교한 정확한 시각 기준이다. `currentPeriodEnd <= now`부터 Free로 본다.
- 폴더·클립·태그·휴지통의 모든 보호된 요청은 동일한 구독 권한 해석기를 거쳐야 한다. JWT의 오래된 플랜이나 구독 조회 API 호출 여부에 의존하지 않는다.
- `status === ACTIVE`만으로 Pro 여부를 판단하면, 해지했지만 이용 기간이 남은 사용자를 잘못 Free로 처리하므로 사용하지 않는다.
- `autoRenew`는 다음 결제를 시도할지 나타내며 현재 Pro 권한을 증명하지 않는다. 유효 플랜 계산은 원시 결제 상태 갱신과 분리한다. Free 판정만으로 `autoRenew`나 `nextBillingAt`를 초기화해 재시도를 중단하지 않는다.
- 기준안은 별도 유예 없이 이용 기간 종료 시 Free 전환이다. 다만 정상 결제도 처리 지연 중 일시 잠금이 생길 수 있다. 유예를 채택하려면 대상 사유, 유한한 `gracePeriodEnd`, 재시도 종료 조건을 먼저 정하고 모든 API에서 같은 기준을 적용한다.
- 해지 상태로 기간이 끝난 사용자는 자동갱신 장애 유예의 대상이 아니다. 결제 실패·처리 중 상태만으로 기간을 무기한 연장하지 않는다.
- 권한 캐시를 도입하면 만료·유예 종료 시각을 넘겨 Pro 결과를 재사용하지 않는다. 결제 성공 시에도 무효화하며 구독 응답에 원시 `plan`과 별개인 `effectivePlan`을 제공한다.

### 결제 신뢰성과 권한 반영의 배포 전제

유효 플랜 계산을 정확하게 바꾸는 것만으로 결제 신뢰성이 보장되지는 않는다. 다음 계약을 함께 마련한다.

1. **성공 결제의 미반영 복구:** 현재 자동갱신은 주문 선점 → 외부 결제 → DB 활성화 순서다. 과금 성공 후 DB 오류·프로세스 종료가 발생하면 같은 주문을 건너뛰는 동작 때문에 권한이 자동 복구되지 않을 수 있다. 주문 식별자로 결제 결과를 대사하고, 성공한 주문의 기간·권한을 중복 없이 반영한다. 미확정 주문의 재시도·종료·운영 개입 기준을 정의하며, 결과를 모르는 주문을 무조건 다시 과금하지 않는다. 유예 기간은 대사를 대체하지 않는다.
2. **최신 해지 의사 보존:** 외부 결제 중 해지가 완료된 뒤 성공 반영이 `autoRenew=true`를 덮어쓰지 않도록 결제 기간 갱신과 자동갱신 의사를 분리한다. 청구 선점 커밋 전에 해지가 확정되면 과금하지 않는다. 선점이 먼저면 이번 청구 결과를 반영하면서 다음 자동결제를 중단하고, 해지 응답에 미확정 결제 유무를 안내한다. 자동 환불은 별도 범위다. 결제 대사 경로도 같은 규칙을 따른다. 이미 결제한 이용 기간 보장과 다음 자동결제 중단은 함께 충족해야 한다.
3. **배치 진행성:** 오래된 `nextBillingAt` 순으로 조회한 실패·미확정 주문을 건너뛰기만 하면 기본 한도 50개가 앞부분을 계속 차지할 수 있다. 처리 가능한 대상 선정 또는 페이지 진행으로 정상 주문의 처리를 보장하고, 실패·미확정 주문에는 별도 재시도·대사 경로를 제공한다. 한 항목의 게이트웨이 예외가 나머지 처리를 중단하지 않도록 격리하고 처리·실패·건너뜀 결과를 관측한다.

관련 구현은 [자동갱신 유스케이스](../src/subscriptions/application/usecases/process-due-auto-renewals.usecase.ts), [구독 저장소](../src/subscriptions/infrastructure/prisma-subscriptions.repository.ts), [해지 유스케이스](../src/subscriptions/application/usecases/update-my-subscription.usecase.ts), [결제 게이트웨이](../src/subscriptions/infrastructure/toss-payments-billing.gateway.ts)다. 외부 결제 응답을 기다리는 동안 DB 잠금을 유지하는 방식으로 이 문제를 해결하지 않는다.

## Free 전환 후 폴더 잠금

> 아래는 검수 당시 기준안과 대안의 비교 기록이다. 현재 구현은 [폴더 접근 문서](free-folder-access.md)를 우선한다. **전체 읽기 허용안과 삭제 후 자동 재선정안은 채택하지 않았다.** 같은 Free 기간에는 선택을 고정하고, 선택 폴더의 복구는 다른 잠긴 활성 폴더가 있어도 허용한다. 별도 태그 유료화·공개 이미지 객체 잠금은 구현 범위 밖이다.

Pro 사용자가 실제 구독 종료 후 Free로 전환될 때 활성 폴더가 둘 이상이면, 첫 폴더 하나만 접근 가능하게 하고 나머지는 잠금 처리한다. 기존 데이터는 자동 삭제하지 않는다.

### 접근 폴더 선정

1. Free 전환 시 활성 폴더를 `order ASC`, `id ASC` 순으로 정렬한다.
2. 첫 번째 폴더 ID를 `freeAccessibleFolderId`로 확정한다.
3. 이 값을 워크스페이스에 영속화하는 것을 권장한다. 폴더 선택은 결제 이력보다 워크스페이스의 접근 상태에 가깝다.

HTTP 요청이 먼저 도착한 폴더를 선택 기준으로 사용하지 않는다. 요청 순서·동시성에 따라 결과가 달라지고, 재정렬을 통한 우회도 가능하기 때문이다.

`freeAccessibleFolderId`가 가리키는 폴더가 삭제되면, 같은 트랜잭션에서 다음 활성 폴더를 같은 정렬 규칙으로 지정한다. 활성 폴더가 없으면 값은 `null`이며, 이후 Free 사용자가 처음 만드는 폴더가 접근 폴더가 된다.

- Free 전환은 한 폴더만 있어도 선정하고, 폴더가 없으면 `null`로 기록한다. 해당 ID는 같은 워크스페이스의 활성 폴더여야 한다.
- 활성 폴더가 있는데 선정 ID가 없거나 잘못된 폴더를 가리키면 같은 잠금·트랜잭션 안에서 정렬 기준으로 복구한다. 정합성 오류를 이유로 모든 폴더를 열어 주지 않는다.
- 만료 배치가 지연되어도 각 보호된 요청은 먼저 유효 플랜과 선정 상태를 확정한다. 만료 후 재정렬·생성·삭제 요청이 이전 Pro 권한으로 먼저 실행되어 선정 결과를 바꾸면 안 된다.
- 만료 직전의 정렬을 기준으로 삼으려면 모든 폴더 변경 경로가 이 순서를 지켜야 한다. 관리 작업 등 예외 경로가 있다면 전환 시점 스냅샷을 별도로 남긴다.
- Pro 재구독 시 잠금은 즉시 해제한다. 이전 선택은 권한 근거로 사용하지 않으며, 다음 Free 전환에서는 당시 정렬로 다시 선정한다. 지연된 만료 작업은 최신 결제 기간을 재확인해 재구독 상태를 덮어쓰지 않는다.
- 선정은 전환별로 멱등적으로 처리한다. 잠금 여부를 모든 폴더에 중복 저장하기보다 유효 플랜과 선정 ID로 계산하고, 전환 세대 또는 버전으로 중복·오래된 작업을 구분한다.

### 삭제를 통한 접근 폴더 변경의 의미

기존 규칙을 유지하면 다른 폴더를 열기 위해 접근 폴더를 삭제할 수 있다. 모든 활성 폴더를 삭제한 뒤 원하는 폴더를 하나씩 복구하는 방식도 가능하다. 동시 접근 1개라는 제한은 유지하지만, 특정 폴더를 재결제 전까지 계속 봉쇄하는 정책은 아니다.

기준안은 데이터 정리를 허용하기 위해 이 전환을 허용한다. 다만 A·B·C가 활성 상태일 때 A를 삭제해 B를 열면, B·C가 활성 폴더 수에 포함되므로 A 복구는 차단된다. A로 돌아가려면 나머지 폴더까지 삭제해야 할 수 있으며, 삭제한 폴더는 휴지통 보존 기간 후 영구 삭제된다. 이는 교대 접근 우회뿐 아니라 연쇄 삭제와 데이터 손실을 유발할 수 있는 정책 문제다.

삭제 화면에 보존 기간을 표시하는 것만으로 충분한 해결로 보지 않는다. 삭제 없는 명시적 접근 폴더 전환 또는 초과 폴더 읽기 허용을 검토하고, 선택 변경·생성·복구 규칙을 함께 확정해야 한다. 본문의 삭제 후 재선정은 현 기준안 설명이며, 제품 정책 확정 전 안전한 사용자 흐름으로 승인된 것은 아니다.

### 잠금 상태의 동작

| 동작                             | 접근 폴더             | 잠긴 폴더                         |
| -------------------------------- | --------------------- | --------------------------------- |
| 폴더 목록                        | 일반 표시             | 이름·정렬 정보와 잠금 상태만 표시 |
| 폴더/클립 열람                   | 허용                  | 차단                              |
| 클립 생성·수정                   | 생성에 Free 50개 제한 적용; 수정 허용 | 차단                              |
| 폴더 이름 수정                   | 허용                  | 차단                              |
| 폴더 재정렬                      | Free에서는 차단       | 차단                              |
| 클립 단건·선택·폴더 내 전체 삭제 | 허용                  | 차단                              |
| 폴더 삭제                        | 허용                  | 정리를 위해 허용                  |
| Pro 재구독                       | 모든 폴더 잠금 해제   | 모든 폴더 잠금 해제               |

Free에서는 폴더 재정렬을 차단한다. 잠긴 폴더 삭제는 콘텐츠 열람 없이 폴더 목록에서 수행하며, 폴더 전체를 휴지통으로 보내는 정리 예외다. 이 예외를 잠긴 폴더 내부의 클립 수정·삭제 권한으로 확장하지 않는다.

폴더 목록 응답에는 `isLocked: boolean`을 추가해 클라이언트가 잠금 UI를 표시할 수 있게 한다. 잠긴 폴더 또는 그 클립의 콘텐츠 조회·변경을 직접 요청하면 `403`과 식별 가능한 오류 코드(예: `PROJECT_LOCKED`)를 반환한다. 위의 폴더 삭제와 아래 휴지통 관리 예외는 허용한다.

## 접근 우회 방지

잠금은 폴더 상세 조회와 폴더별 클립 목록에만 적용해서는 안 된다. 잠긴 폴더의 콘텐츠가 다른 API에서 노출되거나 수정되지 않도록 아래 흐름에도 동일한 폴더 접근 정책을 적용한다.

- 최근 클립, 즐겨찾기, 최근 열람 목록, 검색 결과
- 클립 조회 기록, 좋아요 등록·취소
- 클립 수정, 단건/다중/전체 삭제, 클립 태그 교체
- 폴더 태그 조회·생성·수정·삭제
- 휴지통 목록·커서·복구·영구 삭제

Free 제한 접근 모드의 전역 클립 목록은 접근 폴더의 클립만 반환해야 한다. 소유 여부만 검증하는 것으로는 잠긴 폴더의 클립 ID를 통한 우회를 막을 수 없다.

- 접근 범위를 DB 조회 조건에 적용한 뒤 검색·정렬·페이지 크기 제한을 수행한다. 조회 후 필터링하면 빈 페이지, 잘못된 `hasMore`, 검색 fallback 차이가 생긴다.
- 제목 일치 여부 확인, 커서 검증, 최근 조회 ID 선정, 실제 클립 조회가 같은 범위를 사용한다. 향후 개수·집계·내보내기 API에도 적용한다.
- 일반 클립 목록에서는 Free 전환으로 기존 커서가 잠긴 폴더를 가리키면 내용이나 존재 이유를 노출하지 않는 `404`를 반환하고 클라이언트가 첫 페이지부터 다시 조회한다. 휴지통 커서는 아래에서 허용한 관리 메타데이터 범위로 검증한다.
- 클립 수정의 접근 권한은 저장된 소속 폴더를 기준으로 검사한다. 요청의 `folderId`·`workspaceId`로 소속을 변경할 수 없으며, 잠긴 클립을 접근 가능한 폴더에 속한 것처럼 처리해서는 안 된다.
- 명시적인 다중 ID 요청에 접근 불가 항목이 하나라도 있으면 전체를 거부한다. 전역 조회는 접근 범위로 필터링하고, 폴더 내 전체 삭제는 명시한 폴더의 접근 권한을 검사한다.
- 인증과 소유권 검사를 먼저 수행한다. 타인 데이터와 없는 대상은 동일하게 `404`로 처리하고, 소유자에게만 잠금 사유를 알린다.

## 태그 정책

Free 사용자는 접근 폴더를 포함해 태그 기능을 사용할 수 없다.

- 태그 전용 조회·생성·수정·삭제·클립 연결 및 연결 해제는 `403 FEATURE_NOT_AVAILABLE`로 차단하는 것을 기준안으로 한다.
- `PUT /clips/:clipId/tags`의 빈 배열도 연결 해제이므로 차단한다. 이 API의 태그 자동 생성 경로에도 동일하게 적용한다.
- 일반 검색은 제목 검색만 수행한다. 태그 검색으로의 fallback도 수행하지 않는다.
- 기존 Pro 태그 데이터는 삭제하지 않는다. 태그 필드가 있는 일반 클립 응답에서는 `tags: []`를 반환한다. 목록·최근 열람 등 모든 응답에 적용하고, 클라이언트는 이 빈 배열을 실제 태그 삭제 명령으로 되돌려 보내지 않는다.
- 잠긴 폴더를 포함한 기존 태그 데이터는 Pro 재구독 시 다시 사용할 수 있다.

Free의 일반 클립 내용 수정은 숨겨진 태그를 보존한다. 폴더·클립의 허용된 영구 삭제에 수반되는 태그·연결 삭제는 데이터 수명 처리로 허용한다. 클립 소속 변경은 금지하며, 일반 콘텐츠 수정은 기존 태그 연결을 보존한다. 소속 필드를 포함한 요청은 거부한다. 명시적인 태그 삭제만 별도로 허용하려면 태그 조회와 UI까지 함께 결정해야 한다.

## 플랜별 클립 한도와 기존 데이터

대상 폴더마다 현재 활성 클립 수를 `N`, 해당 작업의 순증가량을 `Δ`, 유효 플랜 한도를 `L`로 계산한다. `L`은 Free 50, Pro 300이다. `Δ > 0`인 생성·개별 복구는 `N + Δ <= L`일 때만 허용한다. 폴더 자체 복구로 기존 내용이 다시 활성화되는 경우는 다음 절의 확정 예외를 적용한다. 자동갱신 해지 직후가 아니라 결제한 이용 기간이 끝나 유효 플랜이 Free로 바뀐 때부터 Free 한도를 적용한다.

| 작업                                          | 한도 검사                                           |
| --------------------------------------------- | --------------------------------------------------- |
| 클립 생성, 개별 삭제 클립 복구                | 소속 폴더에 `+1`; 다중 복구는 고유 클립 수를 합산   |
| 소속 폴더·워크스페이스 변경                   | 플랜·개수와 무관하게 금지                          |
| 내용·이미지 수정    | `Δ = 0`이므로 개수 한도로 차단하지 않음             |
| 클립 삭제 | 해당 폴더의 개수 감소 허용                          |

한도 도입 전의 초과 폴더와 Pro에서 Free로 전환해 50개를 초과한 폴더는 자동 삭제하지 않는다. 접근 권한이 있는 폴더에 다음 정책을 적용한다.

- 기존 클립 열람은 허용한다.
- 내용 수정·삭제를 허용한다. 다른 폴더로 옮겨 개수를 줄이는 기능은 제공하지 않는다.
- 새 클립 생성, 개별 클립 복구는 빈자리가 생길 때까지 차단한다. Free는 49→50, Pro는 299→300까지 한 개 추가할 수 있다. Free 50개·Pro 300개에서 추가는 불가능하다. Free로 전환한 200개 폴더에 하나를 추가하려면 49개 이하로 줄이거나 Pro로 전환해야 한다.

잠긴 폴더는 Free 사용자의 편집 대상이 아니므로, 잠금 상태가 해제되기 전에는 클립 생성·수정·복구 대상이 될 수 없다.

## 휴지통 복구

복구는 활성 데이터 수를 증가시키므로 생성과 같은 수준으로 검사한다.

- Free에 활성 폴더가 이미 있으면 다른 폴더 복구를 차단한다. 잠긴 활성 폴더도 이 개수에 포함한다.
- 활성 폴더가 없을 때 폴더를 복구하면 해당 폴더를 `freeAccessibleFolderId`로 지정한다.
- Free에서는 한 번에 폴더 두 개를 복구할 수 없다. 복구되는 각 폴더도 작업 후 폴더 수에 포함한다.
- 삭제된 폴더에 속한 개별 삭제 클립은 부모 폴더 없이 단독 복구할 수 없다. 부모를 함께 복구하면 부모 복구와 클립 복구를 합쳐 검사한다.
- `itemType + id`로 중복을 제거하고 폴더별 최종 활성 클립 수를 계산한다. 폴더가 자동으로 활성화하는 클립과 명시적으로 복구하는 클립을 중복 집계하지 않는다.
- 여러 항목은 모두 복구하거나 모두 거부한다. 조회 이후 상태가 바뀌었거나 실제 갱신 건수가 검증한 대상과 다르면 롤백한다. 현재 `restoredCount`는 중복 제거한 요청 항목 수이며, 폴더 안에서 자동 활성화된 클립 수를 뜻하지 않는다.

### 한도 초과 기존 폴더의 복구 예외 — 확정

폴더를 삭제하기만 해도 기존 데이터를 되찾을 수 없게 되는 상황을 피하기 위해, #150에서 **폴더 자체의 복구는 허용하고 개별 삭제 클립의 추가 복구는 제한**하기로 확정했다. 예외는 플랜의 폴더 수 제한을 면제하지 않는다.

- Free에서 기존 미삭제 클립 200개가 있는 폴더는 폴더 수·접근 조건을 충족하면 200개 그대로 복구한다. 같은 요청에 개별 삭제 클립을 더 복구해 201개로 만드는 것은 전체 거부한다.
- Pro에서도 기존 미삭제 클립 350개가 남은 폴더 자체는 복구할 수 있다. 이후 개수를 늘리는 작업은 막는다.
- 같은 요청으로 개별 삭제 클립을 하나 더 복구해 351개로 만드는 것은 전체 거부한다.
- Free는 49개가 남은 폴더와 개별 클립 하나를 함께 복구해 50개가 되면 허용한다. Pro는 같은 방식으로 299→300을 허용한다. 다른 폴더의 실패 조건이 있으면 일괄 요청 전체를 거부한다.
- 삭제된 폴더에 새 클립을 생성할 수 없으며, 클립 복구는 기존 소속을 유지한다. 다른 폴더로 옮기는 방식으로 복구하거나 한도를 우회할 수 없다.

이 예외는 삭제 전 상태의 복원이며 새 저장 슬롯을 만드는 기능이 아니다. 폴더 수·접근 조건 때문에 복구할 수 없는 경우의 사용자 흐름은 아래 미정인 폴더 접근 정책에서 해결해야 한다. Free의 클립 한도는 Pro 전환으로 300개까지 늘어나지만 Pro에서도 300개를 넘는 추가 저장은 허용하지 않는다.

### 휴지통 조회·영구 삭제·보존

- 삭제 폴더는 이름·ID·삭제 시각과 복구 가능 여부 등 관리에 필요한 메타데이터만 보여 준다. 내부 클립은 노출하지 않는다.
- 접근 폴더의 개별 삭제 클립은 현재 휴지통 메타데이터를 표시한다. 잠긴 활성 폴더의 삭제 클립은 제목·유형을 숨기고 ID·부모 폴더 ID·삭제 시각·제한 사유만 표시하는 기준안을 제안한다. 이런 관리용 메타데이터와 항목 개수의 노출은 의도적인 예외다.
- 기존 휴지통 응답 DTO는 잠금 표시와 제목 마스킹을 표현하도록 확장해야 한다. 응답에 `canRestore`를 주더라도 실제 복구 시 다시 검사한다.
- 소유자는 잠금이나 한도와 무관하게 휴지통 항목을 영구 삭제할 수 있다. 삭제된 폴더 내부 클립은 현재와 같이 부모 폴더 단위로 정리한다.
- 휴지통 전체 비우기는 숨겨진 항목도 포함한다. UI에 이 범위를 알리고 콘텐츠를 반환하지 않는다.
- 다운그레이드와 잠금 자체는 `deletedAt`을 설정하거나 보존 기간을 시작하지 않는다. 사용자가 삭제한 항목은 기존 휴지통 보존 기간을 따르며 재구독해도 영구 삭제된 데이터는 돌아오지 않는다.
- 복구와 영구 삭제·자동 정리가 경쟁하면 한쪽만 성공해야 한다. 이미지 정리 대상도 실제 영구 삭제된 DB 행에서 확정해, 복구된 클립의 이미지를 지우지 않도록 한다.

## 구현 구조

### 책임 분리

- `subscriptions` 기능 도메인
  - 유효 플랜 판정, 플랜별 폴더 수·클립 추가 저장 한도(Free 50/Pro 300)·태그 권한 정책 소유
  - 결제 기간·유예·권한 버전을 제공하고 갱신·해지·결제 상태 처리
- `workspaces` 기능 도메인
  - `freeAccessibleFolderId`와 접근 전환 상태 소유를 권장
  - 유효 플랜 변화에 따른 선정·무효화·삭제 후 재선정 조정
- `shared/application/ports`
  - 여러 기능 도메인이 소비하는 `SubscriptionEntitlementsPort`, `WorkspaceFolderAccessPort` 계약
- `folders` 기능 도메인
  - 폴더 생성 한도, 잠금 상태 목록 응답, 폴더 수정·재정렬·삭제 규칙
- `clips` 기능 도메인
  - 공유 권한 계약이 제공한 플랜별 한도를 폴더별 생성·증가 검사에 적용, 잠긴 폴더 클립의 읽기·쓰기 차단
  - 복구에서 같은 규칙을 쓸 수 있도록 필요한 최소 정책 계약 제공
- `trash` 기능 도메인
  - 복구 전 한도 및 폴더 접근 규칙 검증

`folders`, `clips`, `trash`는 `subscriptions` 기능 도메인의 내부 레이어를 직접 import하지 않고, 공유 포트를 통해 필요한 권한과 폴더 접근 정보를 받는다.

`workspaces`는 현재 모듈 뼈대만 있으므로 위 책임 배치는 구현 제안이다. 각 기능의 규칙 구현은 소유 기능 안에 두고, 공유 디렉터리에 모든 비즈니스 로직을 모으지 않는다. HTTP DTO와 오류 변환은 presentation, 흐름 조정은 application, 원자적 저장은 infrastructure에서 담당한다.

### 원자성 및 동시성

단순히 `count()` 후 `create()` 하는 방식은 동시 요청에서 한도를 초과시킬 수 있다. 트랜잭션으로 감싸는 것만으로 충분하다고 가정하지 않는다. 아래 작업은 같은 경쟁 제어 규칙 안에서 권한·한도 검사와 변경을 함께 수행한다.

- 폴더 생성
- 클립 생성
- 클립 내용·이미지 수정
- 휴지통 폴더/클립 복구
- 접근 폴더 삭제 후 다음 접근 폴더 선정
- 구독 갱신·만료 전환과 경쟁하는 폴더·클립·태그 변경
- 복구와 경쟁하는 휴지통 영구 삭제·자동 정리

개인 워크스페이스 단위 행 잠금을 공통 쓰기 경계로 사용하는 방식을 우선 검토한다. 최종 DB 트랜잭션에서 잠금을 얻은 뒤 기준 시각을 정하고 최신 구독·선정 상태·소유권·삭제 상태·개수를 다시 읽는다. 이 기준 시각을 해당 쓰기의 권한 판정 시점으로 삼는다. 잠금 대기나 이미지 업로드 전에 확보한 시각과 권한을 재사용하지 않는다.

읽기 요청은 요청별 단일 기준 시각과 일관된 권한 스냅샷을 사용한다. 여러 조회를 조합하는 목록도 같은 접근 범위를 유지한다. 최초 선정·정합성 복구가 필요한 읽기에서는 해당 상태 확정까지 원자적으로 처리한다.

경쟁하는 결제 갱신과 삭제·복구 경로도 같은 경계에 참여해야 한다. 포트의 사전 권한 조회만으로 승인하거나, 포트마다 독립 트랜잭션을 열어 검사와 쓰기를 분리하면 보호가 깨진다. Prisma 트랜잭션 객체를 application에 직접 노출하지 않도록 원자적 저장 계약과 내부 조정 방식을 설계한다.

처리량 때문에 폴더 단위 잠금으로 세분화한다면 구독/워크스페이스 → 폴더 ID 오름차순처럼 잠금 순서를 통일한다. 대안으로 Serializable 트랜잭션을 사용하면 충돌 시 전체 검증을 포함해 횟수를 제한하여 재시도하고, 소진 시 재시도 가능한 충돌 오류를 반환한다. 외부 결제·업로드를 DB 충돌 재시도와 함께 반복하지 않는다.

이미지 생성·교체는 사전 권한 검사 → 외부 업로드 → 최종 DB 재검사·쓰기 순서로 처리한다. 최종 실패 시 이번 요청의 새 객체가 DB에서 참조되지 않는지 확인하고 정리하며, 기존 이미지는 DB 교체가 성공한 뒤 삭제한다. #149의 수정 경로는 참조를 확인할 수 없으면 객체를 보존하고 정리 실패를 기록한다. 영속적인 정리 재시도 작업은 후속 설계 대상이다. 클라이언트 재전송에 따른 중복 생성도 막아야 한다면 별도의 멱등 키 계약을 추가한다.

권한·개수를 다시 검사하더라도 트랜잭션 전에 읽은 콘텐츠를 다시 저장하면 안전하지 않다. 소속 변경을 금지해도 콘텐츠 없는 수정이 기존 이미지 URL을 재저장하면 같은 문제가 남는다. 콘텐츠 없는 요청 A가 이미지 X를 읽은 뒤 요청 B가 이미지 Y로 교체하고 X를 삭제하면, 뒤늦은 A가 삭제된 X를 다시 저장할 수 있다. 다음 규칙을 함께 적용한다.

- 수정 DTO에서 `folderId`·`workspaceId`를 제외하고 기존의 `forbidNonWhitelisted` 검증으로 해당 필드가 포함된 요청을 거부한다. 같은 ID 재전송도 허용하지 않는다.
- 이름·콘텐츠가 모두 없는 빈 수정은 쓰기 전에 `BAD_REQUEST`로 거부한다. 이름(`title`) 단독 수정은 해당 컬럼만 갱신하고 사전 조회한 콘텐츠를 DB에 다시 쓰거나 이미지를 업로드·삭제하지 않는다.
- 저장소는 클립 잠금 안에서 콘텐츠 필드만 원자적으로 갱신하고 실제 교체 전 이미지 URL을 반환한다. 보존할 값과 정리할 이미지는 이 최신 클립을 기준으로 결정한다. 저장된 소속 폴더 기준으로 접근 권한과 삭제 상태를 검증하며 소속을 변경하지 않는다.
- 오래된 콘텐츠 수정 요청을 거부해야 하는 경우 버전 검사를 적용하고 충돌 오류 계약을 정한다.
- 실제로 교체된 이전 객체만 성공 후 정리한다. 콘텐츠 없는 수정/이미지 교체 및 이미지 교체/교체 경쟁에서 최종 DB 참조 객체가 삭제되지 않는지 검증한다.

워크스페이스 단위 잠금은 초기 동시성 제어로 타당하지만, 잠금 전에 만든 오래된 저장 데이터나 외부 결제 성공의 미반영까지 자동으로 해결하지는 않는다.

## API 및 오류 계약

권장 오류 응답은 다음과 같다.

| HTTP 상태 | 오류 코드 예시               | 의미                                                    |
| --------- | ---------------------------- | ------------------------------------------------------- |
| `403`     | `PLAN_LIMIT_EXCEEDED`        | Free 폴더 생성·복구 한도 도달                           |
| `409`     | `CLIP_LIMIT_EXCEEDED`        | 유효 플랜별 폴더당 클립 추가 저장 한도 초과                  |
| `403`     | `PROJECT_LOCKED`             | Free 제한 접근 모드에서 잠긴 폴더/클립 접근 시도        |
| `403`     | `FEATURE_NOT_AVAILABLE`      | Free 사용자의 태그 기능 요청                            |
| `403`     | `FOLDER_REORDER_NOT_ALLOWED` | Free 사용자의 폴더 재정렬 요청                          |
| `404`     | `NOT_FOUND`                  | 미소유·없는 대상 또는 현재 접근 범위 밖의 커서          |
| `409`     | `RESOURCE_STATE_CONFLICT`    | 복구·삭제 등 대상 상태가 변경되어 요청을 수행할 수 없음 |
| `409`     | `CONCURRENT_MODIFICATION`    | 동시 변경 충돌 재시도 소진; 재시도 가능                 |

HTTP 상태와 코드는 제안 계약이며 서버와 클라이언트를 함께 수정해야 한다. 기존 `statusCode`, `message`, `error`는 유지하고 정책 식별용 `code`, 필요한 `details`를 추가한다. 한도 오류에는 권한이 확인된 대상의 `resource`, `limit`, `currentCount`, `requestedIncrease`, `upgradeCanResolve`를 제공한다.

클립 한도 오류의 `upgradeCanResolve`는 유효 플랜이 Free이고 해당 요청의 `currentCount + requestedIncrease <= 300`이면 `true`, 그 외에는 `false`다. 예를 들어 Free 50개에서 1개 추가는 `true`, Free 300개에서 1개 추가와 Pro 한도 초과는 `false`다. 이 값은 클립 개수 제한만을 설명하며 다른 잠금·권한 검사를 면제하지 않는다. 일괄 요청에서 업그레이드로 해결 가능하다고 안내하려면 모든 대상의 추가 후 개수가 Pro 한도를 충족해야 한다. 폴더 수 한도는 Pro로 해소할 수 있다. 오류 우선순위는 입력 형식 → 인증·소유권·존재 → 삭제 상태 → 폴더 잠금 → 기능 권한 → 한도로 고정한다. 일괄 요청도 미소유 항목을 먼저 거부하고 타인 데이터의 잠금·개수를 노출하지 않는다.

폴더 목록에는 `isLocked`를 제공한다. 잠긴 폴더의 클립 제목·태그·미리보기·이미지 URL은 포함하지 않는다. 별도 권한 응답에는 `effectivePlan`, `freeAccessibleFolderId`, `canUseTags`, `canReorderFolders`와 한도를 제공해 클라이언트가 규칙을 중복 계산하지 않게 한다. 이 값들은 UI 안내용이며 서버 검사를 대체하지 않는다.

## 보안 및 운영 고려사항

- 이미지 URL은 현재 공개 base URL을 전제로 한다. 폴더 잠금이 결제 UX 수준이면 API 접근 차단으로 충분할 수 있지만, URL을 아는 사람이 이미지 자체를 열지 못하게 해야 한다면 private 객체 저장소와 서명 URL 전환이 필요하다.
- 서명 URL도 유효 기간 내에는 재사용될 수 있다. 이미 다운로드한 이미지·텍스트와 오프라인 캐시는 서버 잠금으로 회수할 수 없다. 클라이언트는 플랜 전환 시 목록·검색·태그 캐시를 무효화하되 이를 보안 보장으로 설명하지 않는다.
- Free 폴더당 50개·Pro 300개는 저장 공간 총량 제한이 아니다. Pro의 폴더 수, 이미지 크기, 휴지통 저장량, 태그 수, 요청 빈도는 별도의 리소스 정책 대상이다. 폴더를 무제한으로 만들 수 있는 한 새 클립을 여러 폴더에 나누어 생성할 수 있으므로 Free 50개는 플랜별 추가 저장 한도, Pro 300개는 폴더 정리·성능 한도로 구분해 설명한다. 기존 초과 자료 보존 예외도 함께 안내한다.
- 활성 클립 수 조회가 빈번해지면 `Clip(folderId, deletedAt)` 복합 인덱스를 검토한다.
- `currentPeriodEnd` 비교는 서버/DB의 UTC 시각을 기준으로 하고, 클라이언트 표시는 사용자 시간대로 변환한다.
- 한도 초과·잠금 접근·트랜잭션 충돌을 관측 가능한 로그와 메트릭으로 남겨 배포 후 정책 영향을 확인한다.
- 배포 전에 Free 다중 폴더, Free 50개 초과 폴더와 전체 300개 초과 폴더, Pro 종료일 누락, 잘못된 소유 관계를 내용·비밀값 없이 집계한다. 이상 구독을 사전 보정하고, 접근 폴더 선정은 쓰기 경합을 제어한 상태에서 수행한다.
- 스키마·마이그레이션과 하위 호환 응답을 먼저 준비하고 기존 클라이언트의 오류 처리·캐시 전환을 검증한다. 관측 모드에서 예상 차단을 확인한 뒤 모든 관련 API에 정책을 함께 활성화한다. 롤백은 제한 강제를 해제하되 기존 데이터를 삭제하지 않는 방식으로 준비한다.

## 더 나은 제품 방향과 구현 전 결정

### 다운그레이드 경험 대안

| 선택지                                              | 장점                                                         | 비용·주의점                                                                                     |
| --------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 기존 기준안: 한 폴더만 열람·편집                    | 유료 접근 범위가 명확하고 기존 초안과 가까움                 | 데이터 열람을 위해 삭제 또는 재결제를 유도할 수 있고, 휴지통·공개 이미지까지 보호 범위가 복잡함 |
| 초과 폴더 읽기 전용, 한 폴더만 편집                 | 기존 자료를 찾을 수 있고 삭제를 통한 폴더 전환 동기가 줄어듦 | 읽기와 쓰기 권한을 분리해야 하며 유료 플랜의 가치와 태그 읽기 범위를 다시 정해야 함             |
| 모든 폴더의 기존 데이터 사용 허용, 신규 폴더만 제한 | 전환이 단순하고 기존 사용 흐름 보존                          | 단기 Pro 사용으로 여러 폴더를 만든 뒤 Free로 계속 사용하는 것을 허용하는 정책이 됨              |

검수 당시 권장 대안은 **초과 폴더의 읽기를 허용하고 한 폴더만 편집하게 하는 방식**이었으나, 사용자가 우회 가능성을 이유로 채택하지 않았다. 현재는 한 폴더만 열람·편집한다. 데이터 접근성과 삭제 사고 예방 측면에서는 기준안보다 유리하지만, 저장한 자료의 재열람이 핵심 유료 가치라면 유료 전환율까지 더 좋다고 단정할 수 없다. 현재 판단은 정책·코드 분석에 근거하며 제품 성과가 검증된 것은 아니다. 삭제 전환 빈도, 자료 접근 실패, 관련 문의, 유료 전환 등의 근거로 효과를 평가한다.

채택할 경우 위의 전체 접근 차단 표를 수정하고, 편집 폴더 변경 규칙, 기존 태그 열람·검색 범위, 즐겨찾기·조회 기록·내보내기·삭제 권한을 함께 정의해야 한다. 현재 본문의 구현 기준안은 기존 전체 잠금을 유지하므로, 두 방식을 섞어 구현하지 않는다.

전체 잠금을 유지한다면 만료 전에 Free에서 사용할 폴더를 명시적으로 선택하게 하는 UX를 우선 검토한다. 선택이 없을 때만 기존 `order ASC, id ASC`를 사용한다. 만료 후 언제든 선택을 바꿀 수 있게 하면 모든 폴더를 교대로 사용할 수 있으므로, 이를 허용할지 별도 결정한다.

만료 전 선택은 사용자 의도를 반영하지만 만료 후 필요한 폴더가 바뀌는 문제까지 해결하지는 않는다. 모든 기존 폴더 사용 허용안은 단기 Pro로 폴더를 미리 확보하는 사용을 수용할 때 적합하다. 한도 초과 폴더 자체 복구 예외는 #150에서 확정했으며 추가 증가 제한은 유지한다. 나머지 폴더 접근 대안은 선택 변경과 폴더 생성·복구 정책을 함께 놓고 확정한다.
