# 자동갱신 결제 결과 대사와 권한 복구

관련 이슈: [#146](https://github.com/gksktl111/easy-clip-be/issues/146). 자동갱신에서 과금 성공 후 DB 반영 실패 또는 응답 유실이 발생해도 주문을 다시 과금하지 않고 결제 결과를 확인한다. 최초 빌링 인증·최초 결제의 복구는 이번 변경 범위에 포함하지 않는다.

## 처리 계약

1. 외부 과금 전에 `SubscriptionPayment`를 `PENDING`으로 선점한다. 금액·통화·주문번호와 함께 청구 예정일(`renewalDueAt`), 청구 당시 기간 종료일(`renewalPeriodEnd`), 다음 대사 시각을 저장한다.
2. 정상 성공 응답의 주문번호·금액·통화·결제 키·승인 시각을 검증한다. 확인된 성공만 `DONE`과 구독 기간에 같은 트랜잭션으로 반영한다.
3. 응답 유실, DB 반영 실패, 확정되지 않은 응답은 `PENDING`으로 유지한다. 프로세스가 재시작되어도 외부 조회에 필요한 주문번호와 기간 기준은 DB에 남는다.
4. 기존 `POST /subscriptions/auto-renewals/due` 배치를 다시 호출하면 먼저 대사할 주문을 조회한다. 대상 선정은 현재 구독의 `plan`, `status`, `autoRenew`, 빌링키 유무와 독립적이다. 해지·만료한 구독도 과거 성공 결제를 복구할 수 있다.
5. 대사에서는 토스의 `GET /v1/payments/orders/{orderId}`만 호출한다. 같은 주문을 다시 POST 과금하지 않는다. `DONE`이며 저장된 주문번호·금액·통화와 일치하고 유효한 결제 키·승인 시각이 있어야 권한을 반영한다.
6. `PENDING → DONE` 조건부 갱신을 선점한 트랜잭션만 구독을 변경한다. 구독 갱신 실패 시 결제 갱신도 롤백된다. 동일 주문의 동시·반복 처리로 기간을 다시 연장하지 않는다.

기간은 청구 당시 스냅샷과 실제 승인 시각으로 계산한다. 대사 시각을 승인 시각 대신 사용하지 않는다. 이후 다른 결제로 확보한 더 긴 이용 기간은 줄이지 않는다. 최신 `autoRenew`와 빌링키는 덮어쓰지 않으며, 해지된 구독은 기간을 복구해도 다음 청구를 예약하지 않는다. 해지된 사용자의 성공 메일에는 다음 결제가 없음을 표시한다.

구독 조회의 만료 저장도 읽었던 기간과 자동갱신 상태가 그대로일 때만 수행해, 지연된 만료 요청이 복구한 Pro를 덮어쓰지 않게 한다.

DB 잠금은 청구 선점·해지·재개·최종 반영의 짧은 트랜잭션에서 사용한다. 결제 조회 요청은 10초 제한이 있고 DB 트랜잭션 밖에서 수행한다. #148에서 자동갱신 과금 POST에도 10초 제한을 적용한다. 성공 메일은 반영을 선점한 실행에서만 시도하되, 메일의 정확히 한 번 전달이나 프로세스 종료 후 발송 복구는 보장하지 않는다.

API 근거: [토스 결제 조회 API](https://docs.tosspayments.com/reference), [결제 조회 오류 코드](https://docs.tosspayments.com/reference/error-codes). HTTP 404와 `NOT_FOUND_PAYMENT` 조합만 결제 미발견으로 처리한다. 인증 오류·다른 404·서버 오류·네트워크 오류는 미발견이나 결제 실패로 확정하지 않는다.

## 자동 확인과 운영 확인의 경계

- 첫 대사는 과금 선점 시각으로부터 5분 이후 가능하다. 이후 미발견·처리 중·조회 오류는 5분 뒤 재시도한다. 이는 권한 유예나 자동 과금 재시도 정책이 아니다.
- 대사 선점 시 시도 횟수를 증가시키고 다음 시각을 먼저 저장한다. 여러 배치의 중복 조회를 줄이고, 작업자가 종료되면 5분 후 다시 선점할 수 있다.
- 자동 확인은 최대 12회다. 마지막 확인도 완료되지 않으면 `manualReviewAt`과 `reconciliationError`를 기록하고 `reconciliationNextAt`을 비운다. 마지막 선점 직후 작업자가 종료되면 다음 배치가 추가 외부 조회 없이 운영 확인 상태로 전환한다.
- `DONE`의 금액·통화·주문번호·승인 정보 불일치, 취소·부분 취소·중단·만료 상태는 즉시 운영 확인으로 보낸다. 이런 주문을 새 결제로 자동 대체하지 않는다.
- 운영 확인 상태도 `PENDING`이다. 결과 확인 전 권한을 부여하거나 실패로 단정하지 않으며, 해당 구독의 신규 자동갱신 과금을 막는다.
- 배치가 호출되지 않으면 대사도 실행되지 않는다. 기존 `AUTO_RENEWALS_BATCH_ENABLED=true`와 `AUTO_RENEWALS_BATCH_SECRET`을 사용하는 호출 일정을 배포 후에도 유지해야 한다. 비활성화·시크릿 오류는 조회·과금 모두 시작 전에 거부한다. 새 환경변수는 없다.

## 배치 응답 및 관측

`processed`, `succeeded`, `failed`는 이번 실행의 신규 자동갱신 후보·권한 반영·미완료 건수다. #148은 `skipped`를 추가하며 상세 집계는 [배치 진행 문서](auto-renewal-batch-progress.md)를 따른다. `failed`에는 결제 거절뿐 아니라 응답 불확실성과 DB 반영 오류도 포함하므로 청구가 없었다는 근거로 사용하지 않는다. 대사는 별도 `reconciliation` 객체로 반환한다.

| 필드                          | 의미                                   |
| ----------------------------- | -------------------------------------- |
| `reconciliation.processed`    | 이번 실행에서 조회한 대사 후보 수 (#148 기준) |
| `reconciliation.succeeded`    | 이번 실행이 성공 반영을 선점한 주문 수 |
| `reconciliation.deferred`     | 다음 자동 확인을 예약한 주문 수        |
| `reconciliation.manualReview` | 운영 확인 전환을 요청한 주문 수        |

다른 실행이 먼저 완료한 경우 이번 실행의 `processed`가 증가해도 `succeeded`는 증가하지 않을 수 있다. 경합 중의 집계는 운영 안내용이고 DB 행이 최종 상태의 근거다. 기존 운영 확인 주문은 매 실행의 응답에 재집계하지 않으므로 누적 대상도 별도로 관측한다. 로그에는 내부 구독·결제 ID, 고정된 사유 코드와 오류 종류만 남기고 빌링키·배치 시크릿·원시 결제 응답은 출력하지 않는다.

## 이행과 운영 절차

스키마 마이그레이션을 먼저 적용한 뒤 새 코드로 전환한다. 구버전 배치가 새 컬럼 없이 `PENDING`을 만들지 않도록 배치 실행을 일시 중지하고, 실행 중 과금이 끝난 뒤 마이그레이션·애플리케이션 교체를 순서대로 수행한다. 전환 완료 후 배치를 재개한다.

기존 `PENDING` 주문에는 청구 당시 기간 스냅샷이 없으므로 마이그레이션은 `LEGACY_PERIOD_SNAPSHOT_MISSING` 사유로 운영 확인에 보존한다. 현재 구독 기간을 과거의 기준으로 추정해서 자동 연장하지 않는다. 배포 전에 이 주문의 수와 담당자를 확인한다.

운영 확인 대상의 읽기 전용 조회 예시는 다음과 같다. 결과는 내부 운영 환경에서만 확인한다.

```sql
SELECT "id", "subscriptionId", "externalOrderId", "amount", "currency",
       "renewalDueAt", "renewalPeriodEnd", "reconciliationAttempts",
       "reconciliationError", "manualReviewAt"
FROM "SubscriptionPayment"
WHERE "status" = 'PENDING' AND "manualReviewAt" IS NOT NULL
ORDER BY "manualReviewAt", "id";
```

1. 해당 주문의 실제 결제 상태·금액·통화를 토스 조회와 결제 기록으로 확인한다. 결제 미발견을 바로 재과금 근거로 사용하지 않는다.
2. 성공 결제라면 청구 당시의 이용 기간을 확인한다. 기존 주문은 감사 가능한 자료로 `renewalDueAt`과 `renewalPeriodEnd`를 확정해야 한다. 근거가 없으면 수동 권한 보정 여부를 별도로 판단한다.
3. 재대사가 가능한 성공·일시 장애 주문은 권한 있는 운영자가 대상 주문 한 건과 현재 `PENDING` 상태를 확인하는 트랜잭션에서 스냅샷을 보정하고, `manualReviewAt`·`reconciliationError`를 비우며 시도 횟수를 0, 다음 확인 시각을 현재 시각으로 설정한다. 자동 복구 API는 공개하지 않는다. 수행자·근거·변경 전후 값은 운영 기록으로 남긴다.
4. 확인된 취소·실패 주문은 같은 방식으로 해당 주문의 최종 상태와 운영 판단을 기록한다. 성공한 결제의 기간 반영을 제거하거나 주문을 삭제해서 재과금을 유도하지 않는다. 새로운 청구·환불 여부는 별도 정책과 사용자 의사에 따라 결정한다.
5. 배치 실행 후 `DONE`과 기간·자동갱신 상태를 확인한다. 같은 주문을 다시 처리해도 기간이 추가로 늘지 않아야 한다.

## 범위와 후속 작업

- #146은 자동갱신의 미확정 결과 조회와 원자적 권한 복구를 담당한다. 최초 결제의 주문 선점·복구, 환불 정책, 실패 결제의 새 청구 재시도는 포함하지 않는다.
- [#147](https://github.com/gksktl111/easy-clip-be/issues/147)의 청구 선점·해지 순서, 미확정 결제 안내, 재개 처리는 [해지 정책 문서](auto-renewal-cancellation-policy.md)를 따른다. 선점 후 이번 청구는 완료될 수 있으며 다음 자동결제를 중단한다. 자동 환불은 포함하지 않는다.
- [#148](https://github.com/gksktl111/easy-clip-be/issues/148)은 기존 주문을 건너뛰는 페이지 조회, 항목 오류 격리, 과거 자동갱신 `FAILED`의 대사·운영 확인 이행을 구현한다. [배치 진행 문서](auto-renewal-batch-progress.md)를 따른다. 실패 후 새 주문으로 자동 과금하는 정책은 포함하지 않는다.
- 플랜 기반 폴더 잠금은 구현하지 않는다. [잠금 정책 문서](subscription-plan-limits-and-folder-locking.md)의 정책 결정과 전체 API 적용은 별도 작업이다.

## 구현 검증

2026-09-08, 격리된 PostgreSQL 16 `test_db`에서 27개 마이그레이션을 적용했다. 전체 단위 테스트 230개, 결제 복구 DB 통합 테스트 18개, 기존 애플리케이션 E2E 6개를 검증했고 lint와 build도 통과했다. 실제 토스 결제를 발생시키지 않고 게이트웨이의 HTTP 응답을 대체했다.

DB 통합 테스트는 과금 성공 후 DB 실패, 응답 유실, 다른 DB 연결에서의 동시 반영, 트랜잭션 도중 구독 쓰기 실패의 전체 롤백, 최신 기간·해지 보존, 오래된 만료 갱신 거부, 기존 미확정 주문 마이그레이션, 잘못된 결제 정보 거부, 자동 확인 종료를 검증한다.
