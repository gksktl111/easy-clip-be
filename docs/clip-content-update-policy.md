# 클립 소속 고정과 이미지 수정

관련 이슈: [#149](https://github.com/gksktl111/easy-clip-be/issues/149), [#156 이름 단독 수정](https://github.com/gksktl111/easy-clip-be/issues/156).

## 수정 API 계약

클립은 생성 시 정한 폴더·워크스페이스에 종속된다. `POST /clips`의 폴더 지정은 유지하며, `PATCH /clips/:id`는 이름(`title`) 또는 콘텐츠를 수정한다.

- 수정 입력에서 `folderId`를 제거한다. `folderId`·`workspaceId`를 보내면 기존과 같은 ID여도 `400`이다. 기존 전역 `ValidationPipe`의 알 수 없는 필드 거부 규칙을 적용하며 유스케이스에서도 소속 필드를 거부한다.
- 수정에는 `title`, 유효한 `text`, 이미지 `file` 중 하나가 필요하다. `title`만 보내면 이름만 변경하고 현재 콘텐츠·이미지·태그를 보존한다. 이름은 앞뒤 공백을 제거하며 빈 문자열·공백·null·비문자열은 `400`이다. 빈 요청 `{}`와 공백 텍스트도 `400`이다.
- `title`과 콘텐츠를 함께 보내면 명시한 이름을 사용한다. 콘텐츠만 보내면 기존처럼 본문·색상·파일명에서 이름을 만든다. 사용자 지정 이름을 콘텐츠 변경 후에도 유지하려면 `title`도 함께 보낸다.
- 파일과 텍스트를 함께 보낸 경우 기존과 같이 파일을 사용한다. 파일 유형 검증과 텍스트·색상 판별은 유지한다.
- 수정은 태그 연결과 소속을 변경하지 않는다. 이동을 위한 대상 폴더 조회·워크스페이스 변경·태그 해제 경로를 제거한다.

클라이언트는 수정 요청에 소속 필드를 포함하지 않고, 실제 변경할 이름 또는 콘텐츠가 있을 때만 호출해야 한다. 반환하는 클립 응답 필드는 유지한다.

이름만 바꾸는 요청 예시(JSON 또는 multipart):

```http
PATCH /clips/clip-id
Content-Type: application/json

{"title":"새 이름"}
```

이름 단독 변경은 잠근 최신 행의 `title`만 갱신한다. 사전 조회의 본문·타입·이미지 URL을 재저장하지 않고 이미지 정리도 실행하지 않는다. 따라서 조회 뒤 이미지가 교체되어도 새 이미지가 보존된다. #150의 폴더 접근 제한은 이름 변경에도 적용한다.

## 이미지 교체 순서

1. 소유자의 활성 클립을 조회하고 새 파일을 업로드한다. 업로드마다 고유 객체 URL을 사용하며 기존 URL을 재사용하지 않는다. 현재 텍스트 입력은 텍스트·색상으로 처리하므로 이미지 URL을 다시 참조하는 입력 경로가 아니다.
2. 짧은 DB 트랜잭션에서 클립 행을 잠근 뒤 현재 소유권·삭제 상태를 재확인한다. 콘텐츠 필드만 저장하고 같은 잠금에서 읽은 실제 이전 `imageUrl`을 반환한다.
3. 커밋 후 실제로 교체된 이전 이미지를 삭제한다. 처음 조회했을 때의 오래된 URL을 정리 기준으로 쓰지 않는다. 외부 업로드·삭제를 기다리는 동안 DB 잠금을 유지하지 않는다.

동시 수정의 최종 콘텐츠는 DB 쓰기 순서를 따른다. 예를 들어 두 요청이 X를 읽고 각각 Y와 Z를 업로드해 순서대로 저장하면, 첫 요청은 X를, 두 번째 요청은 Y를 정리한다. 최종 Z는 보존된다. 버전 컬럼은 추가하지 않으며, 내용을 쓰지 않는 요청이 과거 URL을 되살리는 경로를 제거한다.

## 저장·정리 실패

- 업로드 후 쓰기가 실패하면 같은 클립 행 잠금을 다시 얻어 앞선 쓰기가 끝난 후의 이미지 참조를 확인한다. 쓰기 응답만 유실됐을 수 있으므로 새 업로드를 무조건 삭제하지 않는다.
- DB가 새 업로드를 참조하면 보존한다. 참조하지 않는 것이 확인되면 새 객체를 삭제한다. 소프트 삭제된 클립의 이미지도 참조로 취급한다.
- DB 조회가 실패해 결과를 확인할 수 없으면 객체를 보존하고 정리 실패를 기록한다. 원래 쓰기 오류를 반환한다. 정리 도중 오류가 나도 원래 오류를 덮어쓰지 않는다.
- 정상 저장 후 이전 객체 삭제가 실패하면 수정 성공은 유지하고 정리 실패를 기록한다.

현재 정리는 요청 안에서 시도하는 방식이다. 프로세스 종료, 업로드 응답 자체의 유실, DB 확인 불가, 저장소 삭제 실패에는 미사용 객체가 남을 수 있다. 커밋 응답 유실 때는 이전 객체 정리도 누락될 수 있다. 이 작업은 영속 정리 큐나 자동 재시도 작업자를 추가하지 않는다. 잔여 객체를 운영 정리할 때는 현재 DB 참조를 확인해야 한다. 최초 클립 생성의 업로드 실패 복구는 별도 범위다.

## 검증·배포

실제 PostgreSQL과 HTTP 경로에서 소속 필드 거부·태그 보존, 빈 수정과 이미지 교체, 서로 다른 DB 연결의 동시 이미지 교체, DB 제약 위반에 따른 롤백, 커밋 응답 유실, 조회 후 삭제를 검증한다. 저장소는 객체 존재 여부를 확인할 수 있는 테스트 대체 구현을 사용하며 실제 R2 객체를 만들거나 삭제하지 않는다.

스키마 마이그레이션과 새 환경변수는 없다. 수정 요청에 소속 필드를 보내거나 빈 수정 요청을 보내는 클라이언트는 배포 전에 요청을 변경해야 한다.
