# 자동갱신 배치 진행과 실패 주문 처리

관련 이슈: [#148](https://github.com/gksktl111/easy-clip-be/issues/148). 오래된 실패 주문이 조회 한도를 차지해 정상 구독의 갱신을 막는 문제를 해결한다. [결제 대사](auto-renewal-payment-reconciliation.md)와 [해지 처리](auto-renewal-cancellation-policy.md)의 결제·기간 보존 규칙을 유지한다.

## 대상 선정과 처리 한도

- 신규 청구는 `PRO / ACTIVE`, 자동갱신 활성, TOSS 제공자, 비어 있지 않은 결제 키, 도래한 청구일을 가진 구독에서 찾는다. 미확정 주문이 하나라도 있으면 대사·운영 확인이 끝날 때까지 신규 청구하지 않는다.
- `nextBillingAt, id` 순서로 페이지를 조회하고, 해당 청구 주기의 정확한 주문번호가 이미 존재하면 상태와 관계없이 건너뛴다. 이전 주기의 확정 실패 이력만으로 현재 주기를 제외하지 않는다.
- 기존 주문을 건너뛴 뒤에도 다음 페이지를 읽어 요청한 `limit`만큼 처리 가능한 후보를 채운다. 페이지당 최대 100행을 읽으며 전체 큐를 메모리에 올리지 않는다. 신규 후보 `limit`과 대사 후보 `limit`은 별도 예산이다. 기본값은 각각 50이다.
- 페이지 이동에는 마지막 청구일과 ID를 사용한다. 청구일이 같아도 다음 행으로 진행한다. 순서·조건에 맞는 복합 인덱스를 추가한다. 건너뛸 이력이 많으면 읽는 페이지 수는 늘어나므로 전체 실행 시간의 고정 상한을 뜻하지 않는다.
- 조회 뒤 다른 실행이 먼저 선점하거나 사용자가 해지할 수 있다. 최종 과금 여부는 기존 구독 잠금·최신 상태 검사·주문번호 유일성으로 결정한다. 이미 있는 주문을 삭제하거나 주문번호를 바꿔 재과금하지 않는다.

## 실패·미확정 주문의 경로

새 과금의 응답 유실·거절처럼 보이는 응답·타임아웃·DB 반영 실패는 `PENDING`으로 보존한다. 주문 조회만 재시도하며, 기존의 5분 간격·최대 12회·운영 확인 전환을 따른다. 실패 후 새 주문을 만들어 자동 과금하는 정책은 포함하지 않는다.

구버전은 외부 응답의 비성공 상태를 `FAILED`로 저장했으므로 이것만으로 실제 미과금을 확정할 수 없다. 마이그레이션은 아직 운영 확인 표시가 없는 과거 자동갱신 `FAILED`를 `PENDING`으로 전환한다.

- 주문번호가 정확히 `sub_<해당 subscriptionId>_<14자리 시각>`인 TOSS 주문만 대상이다. 최초 결제의 시각·UUID 주문은 변경하지 않는다.
- `renewalDueAt`이 있으면 다음 배치의 결과 조회를 예약한다. 결과가 검증되면 기존 원자적 완료 경로로 기간을 한 번만 반영한다.
- 기간 스냅샷이 없으면 `LEGACY_FAILED_PERIOD_SNAPSHOT_MISSING` 사유로 즉시 운영 확인에 보존한다. 현재 구독 기간으로 과거 스냅샷을 추정하지 않는다.
- 주문 ID·실패 시각·실패 코드·원본 응답은 감사 근거로 보존한다. 이미 `manualReviewAt`이 있는 실패 주문은 운영자의 판단을 덮어쓰지 않는다.

이 전환은 과거 실패 이후 새 결제를 한 구독에도 영향을 줄 수 있다. 전환된 미확정 주문이 남아 있는 동안 신규 자동과금은 보류된다. 배포 전에 대상 수·실제 결제 결과·운영 담당자를 확인하고, [운영 대사 절차](auto-renewal-payment-reconciliation.md#이행과-운영-절차)로 처리한다. 영구 제외 후 방치하는 기능이 아니며 운영 확인 큐의 처리 책임이 필요하다.

운영자가 실패를 확정해 종료하면 `FAILED`와 판단 근거를 보존한다. 같은 청구 주기의 주문은 계속 재과금하지 않는다. 성공·일시 장애로 재대사가 필요하면 증빙으로 기간 스냅샷을 확인하고 기존 주문을 `PENDING` 및 재대사 일정으로 되돌린다. 별도 추가 청구·환불은 사용자 의사와 별도 정책에 따라 결정한다.

## 오류 격리와 응답

신규 청구의 선점·과금·완료 처리와 대사의 선점·조회·재예약은 항목별로 오류를 처리한다. 특정 항목 실패 이후에도 다음 대사와 신규 구독 처리를 계속한다. 자동갱신 과금 POST에만 10초 타임아웃을 추가한다. 타임아웃은 과금 실패 확정이 아니며 기존 주문 대사로 이어진다. 최초 빌링키 발급·최초 과금의 타임아웃 정책은 변경하지 않는다.

신규 청구의 `processed`는 선정한 후보 수이며 `succeeded + failed + skipped`와 같다. `failed`는 이번 실행의 미완료·오류 수이므로 미과금 건수를 뜻하지 않는다. `skipped`는 조회 후 선점을 얻지 못했거나 다른 실행이 이미 완료한 경우다. 조회 단계에서 제외된 기존 주문 전체를 집계하는 필드는 아니다.

대사 응답에는 `failed`, `skipped`를 추가하며 `processed`를 조회한 대사 후보 수로 집계한다(기존에는 선점 성공 수). `processed = succeeded + deferred + manualReview + failed + skipped`이다.

| 대사 필드      | 의미                                       |
| -------------- | ------------------------------------------ |
| `succeeded`    | 이번 실행에서 결제·기간을 반영한 수        |
| `deferred`     | 다음 자동 확인을 예약한 수(조회 오류 포함) |
| `manualReview` | 이번 실행에서 운영 확인 전환을 요청한 수   |
| `failed`       | 선점·저장 등 항목 처리를 완료하지 못한 수  |
| `skipped`      | 다른 실행이 선점·완료한 수                 |

항목 오류에서 미확정 결제는 삭제하지 않는다. 대사 선점 후 저장 실패가 나면 선점 때 저장한 5분 뒤 일정으로 재시도할 수 있다. 후보 목록 자체를 읽을 수 없는 DB 장애는 배치 요청 실패로 드러내며 정상 완료로 위장하지 않는다. 응답 수치는 실행 단위 관측이고 최종 결제 상태는 DB가 기준이다. 누적 운영 확인 주문은 기존 읽기 전용 조회로 별도 확인한다.

## 배포와 검증

배치 호출을 중지하고 실행 중인 작업이 끝난 뒤 `20260908070000_recover_failed_auto_renewals` 마이그레이션과 코드를 배포한다. 이 마이그레이션은 데이터 상태 전환과 구독 조회 인덱스 생성을 포함한다. 인덱스 생성 중 구독 쓰기가 대기할 수 있으므로 유지보수 시간을 확보한다. 운영 확인 대상을 점검한 뒤 배치를 재개한다. 새 환경변수는 없다.

회귀 검증은 조회 한도보다 많은 실패·미확정 주문 뒤의 정상 주문 처리, 같은 청구일의 페이지 이동, 이전 주기의 실패 이력, 중복 실행의 단일 과금, 게이트웨이·선점·대사 저장 오류 이후 후속 처리, 구버전 실패 주문의 분류·복구를 다룬다. 외부 결제를 실제로 발생시키지 않고 격리된 PostgreSQL `test_db`에서 검증한다.

2026-09-08 검증: PostgreSQL 16에 28개 마이그레이션 적용, 전체 단위 테스트 238개, 구독 DB 통합 테스트 34개와 기존 앱 E2E 6개 통과. 자동갱신에만 타임아웃을 적용하도록 수정한 후 영향받는 단위 테스트 19개와 구독 DB 통합 테스트 34개를 재검증했다. 린트와 빌드도 통과했다.
